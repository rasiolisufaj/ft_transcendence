### Task 1: The window test pins 10.2

**What it does:** a test-only fix. Today the TOTP tests un-freeze the clock before `verifyCode` runs, and the "two windows out" case uses −90 s, which is three windows. So a regression to `window: 2` passes every test. The rewrite freezes `Date` in the middle of a 30-second window, as 10.2 asks ("tested with `vi.setSystemTime`, no live clock"), and moves the refused case to −60 s.

**Files:** Modify `src/lib/auth/totp.test.ts` (the `vitest` import and the `verifyCode` block).

**Interfaces:** consumes `createSecret(): string` and `verifyCode(secret: string, code: string): boolean` from `totp.ts`, unchanged.

- [ ] **Step 1: Rewrite the `verifyCode` block**

Change the first import to:

```ts
import { afterEach, beforeEach, describe, expect, it, vi } from "vitest";
```

Replace the whole `describe("verifyCode", …)` block with:

```ts
describe("verifyCode", () => {
  const secret = createSecret();
  const totp = new OTPAuth.TOTP({ secret: OTPAuth.Secret.fromBase32(secret) }); // SHA1, 6 digits, 30 s
  // 15 s into a 30-second window, so ±30 s is one window away and −60 s two.
  const NOW = Date.UTC(2026, 10, 4, 12, 0, 15);
  const codeAt = (offsetSeconds: number) => totp.generate({ timestamp: NOW + offsetSeconds * 1000 });

  beforeEach(() => {
    vi.useFakeTimers({ toFake: ["Date"] });
    vi.setSystemTime(NOW);
  });

  afterEach(() => {
    vi.useRealTimers();
  });

  it("accepts the current code", () => {
    expect(verifyCode(secret, codeAt(0))).toBe(true);
  });

  it("accepts a code from the previous window", () => {
    expect(verifyCode(secret, codeAt(-30))).toBe(true);
  });

  it("accepts a code from the next window", () => {
    expect(verifyCode(secret, codeAt(30))).toBe(true);
  });

  it("rejects a code two windows out", () => {
    expect(verifyCode(secret, codeAt(-60))).toBe(false);
  });

  it("rejects a garbage string", () => {
    expect(verifyCode(secret, "000000")).toBe(false);
    expect(verifyCode(secret, "abcdef")).toBe(false);
  });
});
```

### Task 3: A new session after the 2FA step (the navbar bug)

**What it does:** after a password login with 2FA, the nav still shows *Se connecter / S'inscrire* on the dashboard.
- **Cause:** in a Server Action, `redirect()` "performs a client-side navigation" (Next docs, `redirect.md`), which keeps the shared root layout where `Nav` lives. Only setting or deleting a cookie makes the action send the whole UI back (`cookies.md`, *Cookie Behavior in Server Functions*). Password login sets the session cookie, so its nav updates. The 2FA step only updates the session row, so the nav keeps the signed-out render it had on `/login/2fa`.
- **Fix:** what the roadmap's C11 already asks for ("Phase 10 adds the same call after a privilege change"). After a valid code, the action creates a new session, marks it verified, sets its cookie and deletes the pending one. The new `Set-Cookie` refreshes the nav, and the token issued before the second factor stops working.

**Files:**
- Modify: `src/app/[locale]/(auth)/login/2fa/actions.ts` (the session import and two lines at the end of `verifyTwoFactor`)
- Create: `src/app/[locale]/(auth)/login/2fa/actions.test.ts`

**Interfaces:** consumes `createSession(userId): Promise<{ token; expiresAt }>`, `hashToken(token): string` (the token's digest is the `Session.id`), `setSessionCookie(token, expiresAt)`, `invalidateSession(sessionId)` from `session.ts`, and `markTwoFactorVerified(sessionId)` from `totp.ts`. No signature changes.
